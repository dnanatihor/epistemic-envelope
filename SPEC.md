## 1. Purpose and scope

### 1.1 Problem

AI-facing data APIs return three different kinds of statements in one response: results of approved data-quality rules, statistics from automated profiling, and content generated by models. An agent or user reading the response cannot tell which claims are authoritative. The model consuming it treats them all as equally true.

### 1.2 What this project delivers

1. **An open specification** for an *epistemic envelope*: a JSON response structure that separates these layers, carries provenance for each, and declares whether inference is permitted.
2. **JSON Schemas and a conformance suite**, so the spec can be implemented in any language.
3. **A Python SDK** to build, validate, enforce policy on, and render envelopes for LLM consumption.
4. **MCP integration**: a decorator for new tools and middleware for retrofitting existing MCP servers.
5. **A reference MCP server** over a catalog backend (fixture data by default, OpenMetadata optional).

### 1.3 Relationship to other projects

- The MCP Governance Auditor's default policy uses the same key names, so a conformant server produces zero EPI/MAN findings. The validator's error codes map one-to-one to auditor rules (§4.4).
- `mcp-warden` uses `epienv.enforce()` to strip inferences for principals not permitted to receive them.

### 1.4 Prior art and positioning

W3C PROV models provenance generally, and OpenLineage models data lineage. Neither addresses the question an LLM consumer needs answered per response: *which of these statements are certified, measured, or generated?* The envelope is deliberately lightweight and response-scoped. A mapping to PROV is a future extension.

### 1.5 Non-goals

- A certification workflow, policy decision engine, or lineage standard.
- Guaranteeing that inferences are correct. The envelope makes their status visible; it does not validate them.

## 4. The specification (content of `spec/SPEC-ENVELOPE.md`)

### 4.1 Layers

| Layer | Container key | Meaning | Required provenance |
|---|---|---|---|
| Certified | `certified_findings` | Outcome of an approved, rule-based check | `rule_id`, `certified_by`, `certified_at` |
| Observed | `profiling_observations` | Measurement from automated profiling or scanning | `observed_at`, `profile_run_id` |
| Inferred | `ai_inferences` | Content generated or judged by an AI/ML model | `model`, `generated_at` |
| Curated (optional) | `curated_metadata` | Statement authored by a human steward | `authored_by`, `authored_at` |

The curated layer is optional in v0.1 and pending a decision (§11).

### 4.2 Conformance levels

- **Level 1 — Labelled.** For existing APIs that cannot be restructured. Every object carrying a claim includes `epistemic_layer` (one of `certified`, `observed`, `inferred`, `curated`) and that layer's provenance keys. The response root carries `inference_permitted`, and `governance_notice` whenever inferred content is present.
- **Level 2 — Enveloped.** The full structure in §4.3.

### 4.3 Level 2 envelope

```json
{
  "envelope_version": "0.1",
  "subject": {"type": "column", "id": "col_email", "name": "email"},
  "attributes": {"data_type": "varchar", "table": "customers"},
  "inference_permitted": true,
  "governance_notice": "AI-generated content is unverified and not certified.",
  "certified_findings": [
    {"id": "cf-1", "statement": "Email format rule passed", "rule_id": "DQ-17",
     "result": "pass", "value": 0.998, "certified_by": "steward_a",
     "certified_at": "2026-09-20T00:00:00Z", "evidence_uri": null}
  ],
  "profiling_observations": [
    {"id": "po-1", "metric": "null_pct", "value": 0.02, "unit": "ratio",
     "observed_at": "2026-09-20T00:00:00Z", "profile_run_id": "pr_9"}
  ],
  "ai_inferences": [
    {"id": "ai-1", "kind": "classification", "statement": "Likely contains personal email addresses",
     "reported_confidence": 0.9, "model": "provider/model-id", "generated_at": "2026-09-20T00:00:00Z",
     "basis": ["po-1"], "review_status": "unreviewed"}
  ],
  "curated_metadata": []
}
```

Normative rules:

| Code | Rule |
|---|---|
| E001 | `inference_permitted` MUST be present and boolean. |
| E002 | If `inference_permitted` is false, `ai_inferences` MUST be absent or empty. |
| E003 | If `ai_inferences` is non-empty, `governance_notice` MUST be a non-empty string. |
| E004 | Items in `certified_findings` MUST NOT carry inferred provenance keys (`model`, `generated_at`). |
| E005 | Every item MUST carry its layer's required provenance keys (§4.1). |
| E006 | Item `id`s MUST be unique within an envelope. |
| E007 | Every `basis` entry MUST reference an existing item `id`. |
| E008 | `attributes` MUST contain only descriptive structural values (strings, numbers, booleans), never objects that carry layer or provenance keys. |
| E009 | Timestamps MUST be RFC 3339 strings. |
| E010 | `review_status` MUST be one of `unreviewed`, `accepted`, `rejected`. |

Guidance (SHOULD):

- `reported_confidence` is the model's own estimate and is not calibrated. Consumers SHOULD NOT treat it as a probability of correctness. The name is deliberate.
- Inferences SHOULD list their `basis` so consumers can trace a claim to the measurements it rests on.
- Consumers presenting envelopes to an LLM SHOULD keep layers visibly separate (see §5.4).

### 4.4 Mapping to MCP Governance Auditor rules

| Envelope code | Auditor rule |
|---|---|
| E001 | EPI-001 |
| E002 | EPI-008 |
| E003 | EPI-009 |
| E004 | EPI-004 |
| E005 | EPI-005 (certified) / EPI-006 (observed timestamp) |

## 5. Python SDK

### 5.1 Models and validation

- `models.py` mirrors the schema: `Envelope`, `Subject`, `CertifiedFinding`, `Observation`, `Inference`, `CuratedStatement`.
- The committed JSON Schema files are **normative**. Pydantic models are a convenience mirror. A test asserts that every envelope produced by the SDK validates against the schema, and that the validator passes the whole conformance suite.
- `validate(obj: dict, level: Literal[1, 2] = 2) -> list[Violation]` runs JSON Schema validation, then semantic checks (E002–E010) that schemas cannot express. `Violation(code, path, message)`. It never raises on invalid input.

### 5.2 Builder

```python
env = (EnvelopeBuilder(subject=Subject(type="column", id="col_email", name="email"))
       .attributes(data_type="varchar", table="customers")
       .permit_inference(True, notice=DEFAULT_NOTICE)
       .certified(statement="Email format rule passed", rule_id="DQ-17", result="pass",
                  certified_by="steward_a", certified_at=ts)
       .observed(metric="null_pct", value=0.02, observed_at=ts, profile_run_id="pr_9")
       .inferred(kind="classification", statement="Likely contains personal emails",
                 model="provider/model-id", generated_at=ts, reported_confidence=0.9,
                 basis=["po-1"])
       .build())          # raises EnvelopeError listing violations if invalid
```

IDs are auto-assigned (`cf-N`, `po-N`, `ai-N`, `cm-N`) unless supplied.

### 5.3 Enforcement

```python
class InferencePolicy(BaseModel):
    permitted: bool = True
    allowed_kinds: set[str] | None = None        # None = all kinds
    require_review_accepted: bool = False
    notice: str = DEFAULT_NOTICE
    withheld_notice: str = "AI inferences were withheld by policy."

def enforce(env: Envelope, policy: InferencePolicy) -> Envelope: ...
```

When `permitted` is false: `ai_inferences = []`, `inference_permitted = false`, `governance_notice = withheld_notice`. Otherwise inferences are filtered by kind and review status. `enforce` works on Level 1 dicts too via `enforce_labelled(obj, policy)`, which removes objects labelled `inferred`.

### 5.4 Rendering for LLMs

`to_llm_context(env, style="markdown") -> str` renders clearly separated sections in a fixed order:

```
## Certified findings (authoritative)
- [cf-1] Email format rule passed — rule DQ-17, pass, certified by steward_a on 2026-09-20
## Profiling observations (measured; may be stale)
- [po-1] null_pct = 0.02 (observed 2026-09-20, run pr_9)
## AI inferences (unverified; do not present as fact)
- [ai-1] Likely contains personal emails — model provider/model-id, based on [po-1], review: unreviewed
Governance notice: AI-generated content is unverified and not certified.
```

Empty sections render as `- none`. Output is deterministic and snapshot-tested.

## 6. MCP integration

### 6.1 Framework-agnostic core

```python
class Mapper(Protocol):
    def __call__(self, raw: dict[str, Any]) -> Envelope: ...

def shape_response(raw: dict[str, Any], mapper: Mapper, policy: InferencePolicy) -> ShapedResult:
    """Map → enforce → validate. Returns structured dict + text rendering + violations."""
```

A mapping that produces an invalid envelope is a server bug: `shape_response` logs the violations and returns an error result instead of an invalid envelope.

### 6.2 Decorator (new tools)

`@epistemic_tool(mapper=..., policy=...)` wraps a FastMCP tool so that it returns `structuredContent` = the envelope and a text block = `to_llm_context()`. It sets `outputSchema` to the envelope schema and `readOnlyHint` to true unless overridden.

### 6.3 Middleware (existing servers)

`EpistemicMiddleware(mappers: dict[str, Mapper], policy_resolver: Callable[[CallContext], InferencePolicy])` hooks tool calls and applies `shape_response` to tools listed in `mappers`. Other tools pass through untouched. `policy_resolver` receives tool name and, where the framework exposes them, request headers and client info.

**Phase 3 begins with a spike** confirming against the installed `fastmcp` version: (a) middleware can replace a tool result's structured and text content, (b) a decorator can set `outputSchema` and annotations. Record findings in `docs/adr/0001-fastmcp-integration.md`. If (a) is unsupported, ship the decorator plus `shape_response` only and document the limitation.

## 7. Reference server (`examples/catalog_server`)

- `CatalogBackend` protocol: `list_assets()`, `get_asset(id)`, `get_dq_results(id)`, `get_profile(id)`.
- `FixtureBackend` reads `data/seed.json` (default; zero infrastructure). The seed contains 3 tables and 12 columns with DQ results and profiles, including one column with a stale profile and one with a failing rule.
- `OpenMetadataBackend` (optional extra `[openmetadata]`): maps OpenMetadata data-quality test-case results → certified findings and table/column profiles → observations. Uses the REST API via `httpx`. Setup uses OpenMetadata's official Docker quickstart, documented as heavy and optional. Phase 5 starts by verifying endpoint paths against the running version.
- `InferenceProvider` protocol: `StaticInferenceProvider` (canned, for tests and demos) and `LLMInferenceProvider` (generates a description and a sensitivity classification from profile and DQ data; the prompt asks the model to list which observation IDs it relied on, which become `basis`).
- Tools (all `readOnlyHint: true`, `outputSchema` = envelope schema): `list_assets`, `get_asset_profile`, `describe_asset`, `get_quality`.
- Policy: the environment variable `EPIENV_INFERENCE=off` makes the server run with `permitted=false`, to demonstrate enforcement.

## 8. Testing

- **Conformance suite:** at least 12 valid and 20 invalid documents, covering every code E001–E010 at least once and Level 1 and Level 2. For `invalid/E00N-*.json`, `validate()` must return exactly one violation with code `E00N`.
- **Builder:** round-trip (build → dump → validate → load) and error listing.
- **Enforce:** policy matrix (permitted/not, allowed_kinds, require_review_accepted) with expected surviving inference IDs.
- **Render:** golden text files for 4 envelopes (full, no inferences, withheld, all empty).
- **MCP:** in-memory FastMCP client against a test server exposing one decorated tool and one middleware-shaped tool; assert `structuredContent` validates and text equals the render.
- **Reference server:** fixture backend + static inference; with `EPIENV_INFERENCE=off`, no response contains inferences.
- **Cross-project (optional, once the auditor exists):** running the MCP Governance Auditor against the reference server yields zero EPI and MAN findings.

## 9. Phases and acceptance criteria

**Phase 0 — Standard first.** Write `spec/SPEC-ENVELOPE.md` from §4, both JSON Schemas, and the conformance suite. *Accept:* every conformance document is schema-checked by a script; the spec doc has sections for layers, levels, envelope, rules table, guidance, and versioning policy. *Baseline:* the repository baseline in Appendix B.1 is in place, including a README stub with the project name, one-line value proposition, Why, and a planned Quickstart; the CI workflow's commands pass locally.

**Phase 1 — Models and validator.** §5.1. *Accept:* the full conformance suite passes; mypy strict and ruff clean.

**Phase 2 — Builder, enforce, render.** §5.2–5.4. *Accept:* policy-matrix and golden-render tests pass.

**Phase 3 — MCP integration.** Spike + ADR, then §6. *Accept:* in-memory MCP tests pass for both decorator and middleware (or the middleware limitation is documented in the ADR and README).

**Phase 4 — Reference server.** §7 with the fixture backend and static inference. *Accept:* `uv run python -m examples.catalog_server` starts; the reference-server tests pass; README quickstart works in one command.

**Phase 5 — Optional backends and release.** OpenMetadata backend, LLM inference provider, release workflow to TestPyPI then PyPI, and docs site. *Accept:* backend tests pass against recorded HTTP fixtures; the release workflow publishes to TestPyPI on tag. *README:* README.md satisfies Appendix B.2 and B.3; a CI job runs the Quickstart on a fresh checkout and passes; all example output comes from real runs.
